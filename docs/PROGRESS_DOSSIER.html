§1

The problem, in one paragraph

Planning engineers manually transcribe CAD metadata into compliance documentation for low-voltage connections to DB Energie's 50 Hz railway power system. Two failure modes keep recurring: template drift (citing a retired guideline, e.g. Ril 954.0107) and physical parameter errors (a bending radius or pulling force outside spec) — both trigger rejection at Federal Railway Authority (EBA) review, costing weeks per cycle.

Rail50Hz.ai automates the first data layer of that review: upload a DWG plan, get it converted and structured, and have purpose-built agents read, locate, analyze, sketch on, and answer questions about it — grounded in the actual DB Ril / VDE ruleset. Final validation always remains with the human engineer — this is a first-pass assistant, not a sign-off tool.

Ingestion

Dual-engine DWG→DXF: LibreDWG dwg2dxf (open source, default) with ODA File Converter as an optional higher-fidelity fallback.

Extraction

ezdxf entity parsing + shapely spatial math + server-side PNG rendering that recovers block symbols the entity parser can't reach.

Agent layer

5 scoped agents behind one interface, swappable across mock rules / OpenAI / Vertex Gemini with zero call-site changes.

§4

The agentic system

token-frugal by design

Five scoped agents instead of one monolithic assistant. A real plan payload is ~62k tokens raw — every agent below is designed to touch the LLM only when the interaction actually needs one.

Compliance Analyst

Trigger — end of pipeline, automatic

Structured findings against the Ril/VDE ruleset: compliant / non-compliant / warning, with citation, expected vs. actual, and a suggestion.

LLM · digested payload

Plan Copilot (chat)

Trigger — planner sends a message

Free-text Q&A grounded in the payload, the compliance report, regulation excerpts and Cognee guideline recall. Output is guaranteed plain text.

LLM · grounded

Locator

Trigger — "where is X?" intent

Query → search terms → matches against annotations / layer names → world bbox → normalized image bbox → highlight boxes on the canvas.

LLM optional · term expansion only

Analyzer

Trigger — after locate (free) / on click (paid)

Two-tier drill-down: a free deterministic overview for every hit, plus an opt-in AI description per finding — cached after the first click.

LLM · description tier only

Draftsman

Trigger — "draw ..." intent + clicked canvas points

Connects planner-clicked points into a labeled cable-line sketch overlay, computes real-world length via the render's coordinate mapping, and attaches the relevant Ril 954.9101 §4.2 rule reminder (bending radius, pulling force). The source DXF/DWG file is never modified.

§5

CAD engine decision — why not Open CASCADE

A question worth answering plainly for anyone evaluating this build: we evaluated Open CASCADE Technology (OCCT) — the C++ B-Rep kernel behind FreeCAD and CadQuery — as a possible CAD engine, and rejected it for the current 2D pipeline. We didn't take this on faith: every candidate below was downloaded and run against the real DB plan.

EngineTested howVerdict
LibreDWG
dwg2dxf + toolset		 Built from source, run against Kreuzungsplan.dwg Adopted — 31 ms conversion, all 6 AutoCAD generations 2000–2018
ezdxf drawing add-on Rendered the real plan with matplotlib backend Adopted — 1.8 s/plan, recovers block symbols the entity parser misses
Open CASCADE
cadquery-ocp wheels		 Installed 68 MB wheel, built & round-tripped a parametric solid via STEP Rejected (2D) — open-source core reads STEP/IGES only; DWG/DXF import is a commercial add-on Open Cascade sells separately
FreeCAD, QCAD CE, LibreCAD, OpenSCAD, KiCad Surveyed, not installed Each duplicates what ezdxf already gives us, is GUI-first, or is the wrong domain
Engine of record

LibreDWG (dwg2dxf) → ezdxf → shapely for conversion and extraction, ezdxf.addons.drawing for rendering. This stack reads layers, text, blocks and geometry — the actual compliance signal — in milliseconds, with GPL/MIT licensing and no add-on cost. OCCT stays on the roadmap for a genuine future 3D feature: clearance analysis against live parts, switchgear cabinet models, 2D→3D plan lifting.

§7

What's missing

ranked by product impact
Highest

Block-reference content is invisible. INSERT/ATTRIB entities aren't traversed yet — real DB plans keep a meaningful share of annotation text inside blocks. On the original 130-file DWG census, several files parsed to zero text entities for exactly this reason. Single highest-leverage next task.

Highest

In-memory job store, local-disk file storage. A restart or a second Cloud Run instance loses all jobs; no auth, no multi-tenancy, no rate limiting; CORS is wide open. Hackathon-grade, not product-grade.

Medium

DWG engines aren't in the Cloud Run image yet. The deployed POC currently accepts .dxf only — compiling LibreDWG into the Docker image is a straightforward multi-stage build, just not done.

Medium

Draftsman sketches are session-only. Not persisted server-side, not exported back into the DXF — no way yet to hand a finished sketch to a CAD tool.

Medium

Interaction loop is incomplete. Canvas→panel selection, zoom-to-finding, and snap-to-geometry on the draftsman are not built yet.

Medium

Compliance ruleset is narrow. Currently covers bending radius, pulling force and citation drift — a real product needs the full Ril 954.9101 / VDE 0100-520 surface and an export into the actual Erläuterungsbericht format.

§8

Roadmap to a real product

The hardest technical question — can AI agents reliably read and reason over real, messy DB CAD files — is already de-risked against production data. Phase 1 closes the remaining gap between "works on what we extract" and "works on everything in the file."

  1. Phase 1 next

    Data completeness

    Block/INSERT traversal in the DXF parser; legacy POLYLINE/ARC support; re-run against the full DWG census to measure recall improvement.

  2. Phase 2

    Productionize infrastructure

    Firestore/Redis job store, GCS file storage, auth in front of Cloud Run, DWG engine baked into the Docker image, OpenAPI-generated Dart client.

  3. Phase 3

    Compliance depth

    Expand the machine-readable ruleset with DB Ril/VDE subject-matter input; structured export to the Erläuterungsbericht format; per-finding audit trail.

  4. Phase 4

    Sketch → CAD round-trip

    Persist draftsman sketches per job and write them back into the DXF as a real layer; snap-to-existing-geometry.

  5. Phase 5

    Interaction completeness

    Canvas→panel selection, zoom-to-finding, segment-level region membership, Cognee recall caching.

  6. Phase 6 · optional

    Scale & 3D

    Multi-instance Cloud Run with shared state; OCCT-based 3D features — clearance analysis, cabinet models — if the product direction calls for it.
