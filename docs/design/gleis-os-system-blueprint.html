what's running, how it talks, what's next.

01 · The big picture

One engineer, two front doors, one system underneath.

Everything below the fold on this section runs today, on real DWG/DXF files.

There is one backend process, not a swarm — yet. A FastAPI gateway receives the upload, runs it through a background pipeline (DWG→DXF, geometry extraction, metric math), and hands the result to whichever agent a request needs. Both front doors — the Flutter desktop app and the zero-install browser console — talk to the exact same API.

The CAD engine framework and the interactive viewer are the newest layer: a plan can now be read, rendered, and lightly annotated without Flutter at all — and a raw .dwg can be read/edited/written through four interchangeable engines. What's not built yet is the agent that decides what to write — see §07.

03 · Communication, today

Right now, "agents talking" means function calls inside one process.

This is worth saying plainly, because the pitch deck's diagram of an Orchestrator dispatching to five named agents describes the target shape, not today's reality. Today, every "agent" is a Python module that a FastAPI route handler calls directly and waits on, in the same process, on the same machine. There is no message bus, no agent identity, no retry policy — just an HTTP request in, a JSON response out.

The closest thing to orchestration that exists is client-side: a small set of regular expressions in the browser console guess whether a typed message is a question, a "where is" query, or a sketch instruction, and call the matching endpoint. It works well for a single-user prototype. It does not scale to agents that need to call each other, negotiate, or run in parallel.

one HTTP round trip per step · no agent-to-agent hop
04 · Communication, target

The industry has settled on two protocols. We should adopt both.

2025–26 converged on a clean split, now backed by production usage at scale: MCP (Model Context Protocol) standardizes how one agent calls tools and data sources — a CAD engine, a search index, a database. A2A (Agent-to-Agent), originally Google's, now governed by the Linux Foundation with over 150 production adopters, standardizes how one agent calls another agent as a peer rather than as a tool — with its own task, its own confidence, its own right to say "I need more information."

For GLEIS·OS that means: the Orchestrator speaks A2A to the CAD Agent, the Norms Agent, the Calc Agent and the Verification Agent as peers; each of those speaks MCP downward to its own tools — the CAD engine framework, the knowledge base, the geometry math. One protocol for "agent asks agent," one for "agent uses tool." Not a rebuild — a wrapper around modules that already exist.

05 · The knowledge base

RAG isn't a search feature here — it's the guardrail.

Every regulation-grounded answer in the system is required to trace back to an actual retrieved passage from a named file — never a number the model "remembers" from training. That single rule is what turns a general-purpose language model into something a certified engineer can rely on for a legally-mandated document.

Today the knowledge base is a set of folders — general, db — each a selectable "knowledge base" an engineer can scope a question to. Retrieval is straightforward keyword matching over those files, plus an optional long-term memory layer that can recall past guideline lookups semantically. Independent published research on this class of system backs the approach: grounding answers in retrieved source text measurably cuts hallucination, and governed, traceable retrieval is what makes an AI-assisted answer auditable at all.

The guardrail only holds if the corpus is real and current — a stale or incomplete knowledge base produces confident, cited, wrong answers just as easily. Curating it is product work, not a one-time ingestion.

06 · The unbuilt centerpiece

Today the CAD engine executes edits. Nothing yet decides what to edit.

Built today

A engine-agnostic CadEngine interface sits behind four real implementations (ezdxf, LibreDWG, ACadSharp, QCAD). An API endpoint reads a DWG's layers/geometry/text, accepts a list of structured edits — add or remove a piece of geometry or text — and writes a genuinely new .dwg file back through ACadSharp, the one engine proven to round-trip DWG reliably.

The gap: a human still has to supply the exact edit. There is no agent reading "extend the earthing run to the new signal mast" and producing that structured edit itself — only the mechanism to execute one once it's already been specified.

The vision

An agent that takes a plain-language instruction, retrieves the governing SOP or Richtlinie for that exact kind of change, drafts the structured DWG edit that satisfies it, and routes the proposal through a Verification Agent — checking clearances and norms against the same knowledge base — before a human ever sees it. Only after sign-off does the CAD engine write anything.

This is the loop the pitch deck's "human-in-the-loop" circle describes, made concrete for one specific, high-value action: touching the actual drawing.

nothing reaches step 8 without step 6's citation and step 7's human approval — the write is the very last thing that happens.

08 · Non-negotiables

Whatever gets built next, these hold.

Drafting, not decidingEvery agent output is a proposal. Final validation and legal liability stay with the certified engineer — always.
No claim without a citationIf a regulation-grounded answer can't point to the exact retrieved clause, it doesn't ship as an answer.
No silent writesNothing touches the source DWG/DXF without an explicit, reviewable, human-approved step.
Every correction is loggedAn engineer's edit or rejection is training data, not a discarded event — it's how the system gets better.
